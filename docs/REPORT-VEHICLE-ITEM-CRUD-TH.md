## 1. สรุปสิ่งที่ทำได้

หน้า Tab Stock เดิมเป็น “ตารางอุปกรณ์ + ฟอร์มเพิ่มอุปกรณ์” เท่านั้น ไม่มีโครงสร้างแบบจัดการข้อมูลได้จริง
งานนี้ปรับให้เป็นระบบจัดการทะเบียนรถ + อุปกรณ์ประจำรถแบบครบวงจร (Create / Read / Update / Delete)
โดยมีกฎความปลอดภัย 3 ข้อที่บังคับฝั่งเซิร์ฟเวอร์เสมอ

1. ทุกคำสั่งเขียนข้อมูล **ครอบด้วย Database Transaction เดียว** และใช้ row lock (`SELECT … FOR UPDATE`)
   กันการแก้พร้อมกัน
2. **ลบรถถาวรไม่ได้ถ้ามีประวัติผูก** (ประวัติตรวจ / ร่างตรวจค้าง / งานเติมของ) — ระบบตอบ 409 พร้อมตัวเลข
   แล้วเสนอ “งดใช้งาน (Disabled)” แทน ซึ่งเป็นการตั้งสถานะโดยไม่แตะประวัติเดิม
3. เส้นทางเขียนข้อมูลทุกรายการต้องผ่าน `requireAdmin()` ฝั่งเซิร์ฟเวอร์ (ไม่พึ่งการซ่อนปุ่มในหน้าจอ)

ข้อ 3 เป็นการอุดช่องโหว่ที่พบตอนสำรวจโค้ดเดิม: `VehicleController::addItem` และ `updateItem`
ไม่ได้ตรวจสิทธิ์ ผู้ใช้ที่ล็อกอินได้ทุกราย (รวมถึงพยาบาล) เรียก API แก้ master list ของอุปกรณ์ได้

## 2. วิธีใช้งานบนหน้าจอ (สำหรับทีม)

เข้าเมนู **📦 ทะเบียนรถ/อุปกรณ์** (เห็นเฉพาะผู้ดูแลระบบ)

### 2.1 จัดการรถ

| การทำงาน | วิธีใช้ | ฟิลด์ที่เกี่ยวข้อง |
|---|---|---|
| เพิ่มรถใหม่ | ปุ่ม `🚚 เพิ่มรถใหม่` → กรอกฟอร์ม → `บันทึกข้อมูลรถใหม่` | ทะเบียน*, ชื่อเรียก, ยี่ห้อ/รุ่น, สถานะ, เลขไมล์เริ่มต้น, หมายเหตุ, แหล่งรายการอุปกรณ์เริ่มต้น |
| แหล่งรายการอุปกรณ์เริ่มต้น | เลือกได้ในฟอร์มเพิ่มรถ: `ชุดอุปกรณ์มาตรฐาน (แนะนำ)` / `คัดลอกจาก รถคันอื่นที่มีอยู่แล้ว` / `ไม่สร้างรายการเริ่มต้น` | ระบบจะสร้างอุปกรณ์ให้ทันทีหลังบันทึก |
| แก้ไขรถที่เลือกอยู่ | ปุ่ม `✏️ แก้ไขข้อมูลรถ` (ใต้ dropdown เลือกรถ) | แก้ทะเบียน/ชื่อ/ยี่ห้อ-รุ่น/สถานะ/เลขไมล์/หมายเหตุ — ส่งเฉพาะช่องที่เปลี่ยนจริง |
| ลบรถ | ปุ่ม `🗑 ลบรถ` | มี Confirmation Prompt หลายชั้น + Safety Check |
| สรุปสถานะรถที่เลือก | แถบ chip ใต้ dropdown | สถานะ • จำนวนอุปกรณ์ใช้งาน • ประวัติตรวจ • งานเติมค้าง |

พฤติกรรมที่ออกแบบไว้โดยตั้งใจ (ไม่ใช่บั๊ก)

* **รถใหม่จะไม่มียอดคงเหลือบนรถ** — แม้คัดลอกจากคันอื่น ระบบจะคัดเฉพาะ *รายการอุปกรณ์*
  ไม่คัด *ยอดของบนรถ* มาด้วย เพราะยอดต้องนับจากของจริงบนคันใหม่ (ดูหัวข้อ 5.4 สำหรับหลักฐาน)
* **แก้ทะเบียนแล้วชื่อจะปรับตาม** — ชื่อประจำรถเดิมมักมี `(ทะเบียน)` ต่อท้าย เช่น
  `รถทดสอบ E2E (MOCK) (MOCK-E2E 9999)` เมื่อแก้ทะเบียนเป็น `MOCK-E2E 8888` ชื่อจะตามไปเป็น
  `… (MOCK-E2E 8888)` เพื่อไม่ให้ dropdown แสดงทะเบียนที่ไม่มีอยู่ในระบบแล้ว
* **กดบันทึกทั้งที่ยังไม่แก้อะไร** ระบบจะเตือน `ยังไม่มีข้อมูลที่ต้องแก้ไข` และไม่ยิง request
* **หลังแก้รถ หน้าจะยังเลือกคันเดิม** (ไม่เด้งกลับไปรถคันแรก)

### 2.2 จัดการอุปกรณ์ประจำรถ (การ์ด 1 ใบ = 1 อุปกรณ์)

กรองตามรถได้จาก dropdown **เลือกรถ** — การ์ดที่แสดงคืออุปกรณ์ของรถคันนั้นเท่านั้น
(รวมแถวที่ “พักใช้งาน” เพื่อให้เปิดกลับหรือลบได้)

| การทำงาน | วิธีใช้ |
|---|---|
| เพิ่มอุปกรณ์ | ปุ่ม `+ เพิ่มอุปกรณ์` → กรอก ชื่อ*, จำนวนมาตรฐาน*, วันหมดอายุ, เป็นแบตเตอรี่, **ยอดคงเหลือบนรถ**, สต็อกปัจจุบันในคลัง, จุดเตือนขั้นต่ำ → `เพิ่มอุปกรณ์` |
| แก้ไขอุปกรณ์ | แก้การ์ดแล้วกด `บันทึก` — ส่งเฉพาะช่องที่แก้ (ชื่อ/จำนวนมาตรฐาน/วันหมดอายุ/แบตเตอรี่/ยอดคงเหลือบนรถ) |
| พักใช้งาน / เปิดใช้งาน | ปุ่ม `พักใช้งาน` / `เปิดใช้งาน` บนการ์ด |
| ลบอุปกรณ์ | ปุ่ม `ลบ` → มี Confirmation Prompt → ถ้าอุปกรณ์เคยถูกใช้ตรวจหรือมีงานเติมค้าง ระบบจะ **พักใช้งานแทน** เพื่อไม่ให้ประวัติย้อนหลังขาด |

สองเรื่องที่ต้องทราบเวลาใช้จริง

* **“ยอดคงเหลือบนรถ” กับ “สต็อกในคลัง” คนละยอดกัน** — ฟิลด์แรกคือของบนรถคันนั้นจริง ๆ
  (เขียนลง `refer_items.current_qty` พร้อมประทับเวลา) ฟิลด์หลังคือคลังกลางซึ่งนับรวมตาม
  *ชื่ออุปกรณ์* ทุกคันใช้ยอดเดียวกัน
* **การ์ดจะเว้นว่างช่องยอดคงเหลือถ้า “ยังไม่เคยตรวจนับ”** — ระบบแยกแยะด้วย `stock_updated_at`
  ไม่ใช่ตัวเลข 0 (0 คือ “นับแล้วพบว่ามีศูนย์”) ถ้ายังไม่นับจะขึ้นข้อความ `ยังไม่เคยตรวจนับ`

## 3. API ที่เพิ่ม/ทำให้เป็นทางการ (ตามคำสั่งข้อ 3)

| Method + Path | Controller action | สิทธิ์ | Transaction |
|---|---|---|---|
| `POST /api/vehicles` | `VehicleController::store` | admin | ✅ เดียวทั้งการสร้างรถ + ชุดอุปกรณ์เริ่มต้น |
| `PUT /api/vehicles/{id}` | `VehicleController::update` | admin | ✅ + `FOR UPDATE` ล๊อคแถวรถ |
| `DELETE /api/vehicles/{id}` (body `mode = auto\|disable\|force`) | `VehicleController::destroy` | admin | ✅ |
| `POST /api/vehicles/{carId}/items` | `VehicleController::addItem` | admin | ✅ อุปกรณ์ + คลังกลาง ใน tx เดียว |
| `PUT /api/items/{id}` | `VehicleController::updateItem` | admin | ✅ |
| `DELETE /api/items/{id}` (body `mode = auto\|disable`) | `VehicleController::deleteItem` | admin | ✅ |

เส้นทาง `/api/admin/vehicles*` และ `/api/admin/items*` แบบเดิมยังใช้ได้ (backward compatible)
แต่ถูกเปลี่ยนให้ **เรียก VehicleService ตัวเดียวกัน** — เดิมสองเส้นทางนี้มีการเขียนซ้ำที่พฤติกรรมไม่เท่ากัน
(เช่น `updateVehicle` ฝั่ง admin แก้ได้แค่ชื่อ, และการลบรถไม่มีอะไรป้องกันเลย)

กลไกที่รองรับงานนี้ฝั่ง backend

* `app/Services/VehicleService.php` (ใหม่) — เป็น single source of truth ของ CRUD รถ/อุปกรณ์
* `app/Exceptions/ApiException.php` (ใหม่) — พา status code + payload (เช่นตัวเลข `blockers`) กลับไป
  ตอบ 409/422 ได้ โดยยังคงถูก `catch (\RuntimeException)` เดิมจับได้
* `StockService::receive/adjust/setStockForItemName` แก้ให้เป็น nested-safe (`$ownsTx = !$db->inTransaction()`)
  เดิมถ้า VehicleService เรียกใน transaction ของตัวเองจะได้ fatal error “Already in a transaction”
* `Vehicle::lockById()` (ใหม่) + แก้ `Vehicle::getItems()/getActiveItems()` ที่พังอยู่เดิม
  (เรียก `->where()` ต่อบน array และใช้ `$this->primaryKey` ผิดตำแหน่ง)

## 4. การเปลี่ยนแปลงโครงสร้างฐานข้อมูล (วิเคราะห์ผลกระทบแล้ว)

**Migration 007 — `database/migrations/007-default-items.sql` (แบบ additive เท่านั้น รันแล้ว)**

เก็บ “ชุดอุปกรณ์มาตรฐาน” ไว้ 1 แถวในตาราง `refer_metadata` ที่มีอยู่แล้ว (`id = 'default_items'`)
ไม่สร้างตารางใหม่ ไม่แก้คอลัมน์เดิม ไม่ลบข้อมูลเดิม

```
payload = { source_car_id, source_label, updated_at,
            items: [ {name, standard, expiry_text, is_battery, target_qty, unit}, … ] }
```

ต้นฉบับสกัดจาก **รถที่มีรายการอุปกรณ์ที่ใช้งานอยู่มากที่สุดที่มีอยู่ในระบบจริง**
(ผลรันจริง: `source_car_id = car-1`, `items = 64` แถว) พร้อมบันทึกที่มาไว้ให้ผู้ดูแลตรวจได้ว่า
ชุดมาตรฐานมาจากคันไหน ไม่ได้เดาขึ้นใหม่

* ผลกระทบ: `refer_metadata` จาก 2 แถว → 3 แถว · rollback: `DELETE FROM refer_metadata WHERE id='default_items';`
* ถ้าแถวนี้หาย ระบบยังทำงานได้ (fallback ไปใช้รายการของรถที่มีข้อมูลมากที่สุดในระบบ)
* สกัดการรันซ้ำด้วย `WHERE NOT EXISTS`

**ข้อจำกัดทางเทคนิคที่เจอจริงระหว่างรัน migration**: MariaDB 10.4 ที่ใช้อยู่ **ไม่มี `JSON_ARRAYAGG()`**
(มีตั้งแต่ 10.5) และ **ไม่มี operator `->`** จึงต้องประกอบ array ด้วย `GROUP_CONCAT(JSON_OBJECT(...))`
แล้วใส่ `[ ]` เอง และอ่านด้วย `JSON_EXTRACT()` — ตรวจความถูกต้องด้วย `JSON_VALID()` ก่อน INSERT จริง

## 6. บั๊กเดิมที่พบตอนสำรวจ แล้วแก้พร้อมมีหลักฐานการทดสอบ

สองข้อนี้เป็นของเดิมก่อนงานนี้ (ไม่ได้เกิดจากโค้ดใหม่) และจัดเป็นความเสี่ยงต่อข้อมูลจริง:

1. **วันหมดอายุที่กรอกตอนเพิ่มอุปกรณ์หายไป** — `handleAddItem` อ่านค่า `#stockExpiry`
   แต่ไม่ใส่ใน payload ทำให้กรอกเท่าไหร่ก็ไม่บันทึก · แก้แล้ว · พิสูจน์ด้วยการทดสอบข้อ 7 (ตารางหัวข้อ 5.2 — DB มี
   `expiry_text=2030-01-15`)
2. **ช่อง “วันหมดอายุ” แบบ date มีสิทธิ์ลบข้อมูลเดิมทิ้ง** — `refer_items.expiry_text`
   เป็นข้อความอิสระ ไม่ใช่วันที่ (ตรวจจริง: **324 จาก 381 แถวไม่ใช่รูปแบบ `yyyy-mm-dd`** เช่น `"10"`)
   `<input type="date">` รับค่าแบบนี้ไม่ได้ จึงแสดงว่าง แล้วการกด “บันทึก” ครั้งถัดไป
   จะส่ง `expiry_text=""` ไปล้างค่าเดิมเงียบ ๆ · แก้เป็นเลือกชนิด input ตามรูปแบบค่าจริง
   ทั้งในการ์ดอุปกรณ์และในแผงคัดลอกรายการ (copy preview) · พิสูจน์ด้วยการทดสอบข้อ 18: แก้ `standard`
   ของแถวที่มี expiry เป็น `"10"` แล้ว `expiry_text` ยังเป็น `10` อยู่ + console ว่างเปล่า

## 7. ส่วนที่ยังไม่ได้รับการยืนยันจากการทดสอบจริง (ยืนยันจากการอ่านโค้ดเท่านั้น)

ต้องพูดให้ตรงตามที่สั่งไว้ว่า “อย่าสรุปว่าระบบถูกต้องเพียงเพราะหน้าเว็บแสดงผลได้” — เหล่านี้ยังไม่ได้พิสูจน์:

1. **เส้นทาง “อุปกรณ์ถูกใช้งานแล้ว → พักใช้งานแทน” (ระดับ item, `mode=auto` → `auto_disabled`)**
   ยังไม่ได้รันทดสอบจริง เพราะการจะพิสูจน์ต้องลองลบอุปกรณ์ที่มีประวัติผูกซึ่ง **เป็นอุปกรณ์จริง**
   และการตั้ง `active=0` คือการแก้ไขข้อมูลจริง จึงไม่ได้ทำ (เส้นทางนี้ถูกพิสูจน์แล้วในระดับ *รถ* — การทดสอบข้อ 12)
2. **`PUT /api/vehicles/{id}` เมื่อทะเบียนซ้ำกับคันอื่น (409)** — ยังไม่ได้รันทดสอบ
   (logic มีใน `VehicleService::updateVehicle` + `firstWhere('plate')`)
3. **เส้นทาง `/api/admin/vehicles*` และ `/api/admin/items*` (mode write ทั้งหมด)** —
   refactor ให้เรียก VehicleService ตัวเดียวกันแล้ว แต่รอบทดสอบนี้ยิงผ่าน `/api/vehicles*` เท่านั้น
   (เส้นทาง admin ขา *อ่าน* ถูกทดสอบผ่านหน้า Tab Stock อยู่แล้ว)
4. **Role-level authorization แบบ “พยาบาล → ต้องได้ 403”** — **ทดสอบไม่ได้ในสภาพแวดล้อมนี้**
   เพราะ (ก) รหัสผ่าน admin ในเครื่องdevไม่ได้เป็นค่า default และไม่มีเก็บในรีโป จึงเปิด session
   ด้วย curl ไม่ได้ และ (ข) การสร้างบัญชีทดสอบใหม่ใน `refer_users`/`refer_nurses` บนฐานข้อมูลที่
   ทีมงานจริงใช้อยู่ถูกระงับไว้ตามข้อกำหนดความปลอดภัย · ที่พิสูจน์ได้จริงคือ `401 Login required`
   (การทดสอบข้อ 17) และการตรวจ `requireAdmin()` ในโค้ดของทุก action เขียนข้อมูล —
   **จึงยังไม่มีหลักฐานจากการรันจริงว่า staff ได้ 403**
5. **การระบุตัวผู้ดำเนินการ** — บัญชี admin ที่ใช้ทดสอบเป็นบัญชีร่วม (`refer_users.id = ''`,
   `username=admin`) Ledger จึงขึ้น `by_name = "Admin User"` โดยไม่มี id ที่ระบุตัวได้
   ตามข้อจำกัดที่ทีมรับทราบอยู่แล้ว — *อ้างไม่ได้ว่าการทดสอบนี้ระบุตัวบุคคลได้อย่างน่าเชื่อถือ*
6. **หน้าตาบนมือถือ / device จริง** — ยังไม่ได้ตรวจด้วย screenshot (browser surface ไม่มี viewport
   ยืนยันได้: `NATIVE_BROWSER_VIEWPORT_UNAVAILABLE`) การตรวจรอบนี้เป็นการตรวจ DOM/ข้อมูล
7. **การอ่านค่าจาก UI โดยผู้ใช้จริง (human acceptance)** — ยังไม่ได้ให้ทีม Refer ลองใช้งานจริง

## 8. ข้อมูลคงเหลือจากการทดสอบ (ต้องขออนุญาตก่อนลบ)

ลบข้อมูลจำลองที่เกี่ยวกับรถ/อุปกรณ์ไปแล้วทั้งหมด (รถ 0 คัน, อุปกรณ์ 0 รายการ — ตรวจแล้วคงเหลือ 0)
แต่ **แอปไม่มีฟังก์ชันลบรายการคลังกลาง** (`refer_stock_items`) จึงเหลือ 4 แถวที่ขึ้นต้นด้วย MOCK:

| ตาราง | แถวคงเหลือ | สถานะปัจจุบัน |
|---|---|---|
| `refer_stock_items` | `stk-76fd07b88b42c1ab2029010d3c40c8a8` ชื่อ `MOCK-E2E อุปกรณ์ทดสอบ` | ปรับเป็น `current_qty=0`, `min_qty=0` แล้ว → ไม่โผล่ในรายการเตือนคลัง (`status="unset"`) |
| `refer_stock_transactions` | 3 แถว ledger (`INIT 20` + `ADJUST 0` + `ADJUST min`) ของชื่อนี้ | เป็นประวัติกดของจริง ไม่ควรแก้ตัวเลขย้อนหลัง |

ถ้าต้องการให้สะอาดจริง รัน SQL นี้ (ยังไม่ได้รัน — รออนุญาตก่อน เพราะเป็นการลบแถวในฐานข้อมูลที่ทีมจริงใช้อยู่):

```sql
DELETE FROM refer_stock_transactions WHERE name LIKE 'MOCK-E2E%';
DELETE FROM refer_stock_items        WHERE name LIKE 'MOCK-E2E%';
```
