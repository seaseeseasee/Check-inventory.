## 1. สรุปสิ่งที่เพิ่มในเวอร์ชันนี้

1. **เมนู 6 แท็บ** ใหม่: หน้าแรก / ตรวจเช็ครถ / เบิก–เติมอุปกรณ์ / ประวัติตรวจ–เติม / ทะเบียนรถ-อุปกรณ์ / ผู้ใช้งาน-พยาบาล
2. **Dashboard เพิ่มสถิติ**: รถทั้งหมด, ตรวจแล้ววันนี้, ร่างตรวจค้าง, ต้องติดตาม, **รอเติม, เติมไม่ครบ, ใกล้หมดอายุ** (แสดง 0 เมื่อไม่มีข้อมูล ไม่มีตัวเลขสมมติ) พร้อมการ์ดรถคันละใบ มีปุ่ม "ตรวจคันนี้" และ "แจ้งเติมคันนี้"
3. **ระบบเบิก–เติมอุปกรณ์** ครบวงจร: สร้างคำขอ (ร่าง/ส่ง) → จ่ายของจากคลัง (ได้บางส่วน) → เติมลงรถจริง (แยกจากการจ่าย) → ยืนยันเติมครบ / ยกเลิกพร้อมเหตุผล ทุกขั้นตอนบันทึกไทม์ไลน์ผู้ดำเนินการ
4. **ประวัติรวมตรวจ+เติม**: สลับมุมมองได้ กรองตามรถ/สถานะ/ช่วงวันที่ + ค้นหาข้อความ
5. **ตรวจจับใกล้หมดอายุ**: อ่านวันหมดอายุรูปแบบ วว/ดด/ปปปป (ทั้ง พ.ศ. และ ค.ศ.) แจ้งเตือนเมื่อเหลือ ≤ 60 วัน หรือหมดอายุแล้ว แสดงบน Dashboard
6. **เชื่อมรอบตรวจ → คำขอเติมอัตโนมัติ**: บันทึกผลตรวจแล้วระบบเสนอแจ้งเติมทันที พร้อมพรีฟิลรายการขาด/ใช้ไป และกันสร้างคำขอซ้ำจากรอบตรวจเดียวกัน (ทั้งฝั่งหน้าเว็บและฝั่ง api.php)

## 3. โครงสร้างฐานข้อมูลที่เพิ่ม

```
refer_restock_requests  หัวคำขอ: id, no(เลขที่ RT-YYYYMMDD-NNN), car_id(FK),
                        car_name(สำเนา), check_id(สำเนาอ้างอิงรอบตรวจ ไม่ผูก FK
                        เพราะประวัติตรวจถูกล้างได้), created_by(FK nurses),
                        created_name, reason, note, status, created_at
refer_restock_items     รายการของ: request_id+item_id(PK), sort_order, name,
                        standard, actual_qty(มีจริง), qty_requested(ขอเติม),
                        qty_issued(จ่ายแล้ว-สะสม), qty_filled(เติมแล้ว-สะสม)
refer_restock_actions   ไทม์ไลน์: request_id+seq(PK), type(create|submit|issue|
                        fill|fulfil|cancel), at, by_id(FK nurses), by_name,
                        note, lines(JSON รายละเอียดจำนวนต่อรายการ)
```

ทุกตาราง InnoDB/utf8mb4 ตาราง items และ actions ผูก FK `ON DELETE CASCADE` ไปที่ requests

## 4. ขั้นตอนอัปเดตระบบเดิม (v4 → v5)

1. **สำรองข้อมูลก่อนเสมอ**
   ```sql
   mysqldump -u USER -p DBNAME > backup-v4-$(date +%Y%m%d).sql
   ```
2. นำเข้า `migrations/001-add-restock.sql` ผ่าน phpMyAdmin หรือ CLI:
   ```bash
   mysql -u USER -p DBNAME < migrations/001-add-restock.sql
   ```
   สคริปต์ใช้ `CREATE TABLE IF NOT EXISTS` รันซ้ำไม่พัง ไม่แตะตารางเดิม
3. อัปโหลดทับ `public/api.php` และ `public/index.html`
4. เปิดหน้าเว็บ ล็อกอิน กดแท็บ "🧰 เบิก–เติมอุปกรณ์" — ถ้าตารางยังไม่ถูกสร้าง หน้าเว็บจะยังใช้งานได้ แต่การบันทึกคำขอเติมจะถูกปฏิเสธพร้อมข้อความให้รัน migration ก่อน
5. ทดสอบตามข้อ 8

**ความเข้ากันได้ย้อนหลัง**: ไคลเอนต์ v4 เก่า (แท็บเดิม) ที่ยังเปิดค้างไว้จะ PUT state โดยไม่มีคีย์ `restocks` — api.php จะ**ไม่ลบ**แถว restock ที่มีอยู่ (เงื่อนไข `array_key_exists`)

## 5. เวิร์กโฟลว์เบิก–เติม (สถานะ)

```
[draft ร่าง] --submit--> [submitted รอดำเนินการ] --issue(จ่ายของ)--> [partial]
                             |                        --fill(เติมลงรถ)--> [partial]
                             |--issue/fill ได้หลายครั้ง (จำนวนสะสม)--> [partial]
                             |--fulfil--> [fulfilled เติมครบ]  (ปิดคำขอ)
                             |--cancel(ต้องระบุเหตุผล)--> [cancelled]
[draft] --cancel(ต้องระบุเหตุผล)--> [cancelled]
```

- **จ่ายของ (issue)** = หน่วยพัสดุจ่ายออกจากคลัง — ยังไม่ถือว่าของถึงรถ
- **เติมลงรถ (fill)** = ผู้ตรวจยืนยันว่าใส่ลงรถจริง — สองขั้นแยกกันตามสเปค
- จำนวนจ่าย/เติมเป็นแบบสะสม (เช่น จ่าย 1 ครั้งละ 1 สองครั้ง = 2) และรับค่าข้อความได้ (เช่น "1 ชุด")
- **กันซ้ำ**: 1 รอบตรวจ (checkId) มีได้คำขอที่ยังไม่ยกเลิกได้คำขอเดียว — บังคับทั้งใน UI และ validateRestocks() ฝั่งเซิร์ฟเวอร์
- บันทึก "มาตรฐาน/ชื่อ" เป็นสำเนา ณ วันแจ้ง — แก้ทะเบียนทีหลังไม่กระทบคำขอเก่า
- การเติม**ไม่ไปแก้จำนวนมาตรฐาน**ในทะเบียนรถ (จำนวนมาตรฐานคือค่าเป้าหมาย ไม่ใช่ stock คงเหลือ) และ**ไม่แก้ประวัติการตรวจ**ต้นทาง

## 6. API (ไม่มี endpoint ใหม่)

ใช้กลไกเดิมทั้งหมด — คีย์ `restocks` เป็นส่วนหนึ่งของ state:

| Action | Method | การเปลี่ยนแปลง |
|---|---|---|
| `api.php?action=login` | POST | ไม่เปลี่ยน |
| `api.php?action=logout` | POST | ไม่เปลี่ยน |
| `api.php?action=state` | GET | เพิ่มคีย์ `data.restocks[]` (โครงสร้างตามข้อ 3) |
| `api.php?action=state` | PUT | รับ `data.restocks[]` เข้า validateState → writeState ใน transaction เดียวกับ revision lock เดิม; **ถ้าไม่ส่งคีย์ restocks แถวเดิมถูกเก็บไว้** |

ความปลอดภัยคงเดิม: PDO prepared statements ทุกคำสั่ง, ตรวจ Origin, session 8 ชม. HttpOnly/SameSite=Strict, rate limit login 8 ครั้ง/นาที, บังคับ HTTPS, ตรวจสถานะ↔การกระทำสุดท้ายของคำขอฝั่งเซิร์ฟเวอร์เสมอ (หน้าเว็บถูกแฮกก็ส่งสถานะมั่วไม่ได้)

## 7. ข้อจำกัดที่ต้องรายงานตามสเปค

1. **บัญชีร่วมรหัสเดียว**: ระบบยังใช้รหัสผ่านระบบเดียวร่วมกันทุกเครื่อง ชื่อ "ผู้แจ้ง/ผู้ดำเนินการ" คือชื่อที่ผู้ใช้เลือกเองในหน้าเว็บ **ไม่ใช่ตัวตนที่พิสูจน์แล้ว** — ไทม์ไลน์จึงเป็นหลักฐานบันทึกการดำเนินการ ไม่ใช่หลักฐานทางบัญชีที่ผูกตัวบุคคลอย่างเชื่อถือได้
2. **ไม่มีตาราง stock คงเหลือ**: ระบบบันทึกการขอ/จ่าย/เติมต่อคำขอเท่านั้น ไม่นับยอดคลังคงเหลือ (ยังไม่มี refer_stock_movements ตามที่สเปคเผื่อไว้)
3. **การเติมไม่อัปเดตจำนวนจริงในรถ**: จำนวน "มาตรฐาน" ยังเป็นค่าตั้งต้น การเติมเสร็จแล้วยอดของในรถต้องดูจากคำขอล่าสุด
4. **ลบคำขอไม่ได้**: คำขอที่ส่งแล้วแก้ไม่ได้ มีแต่ยกเลิกพร้อมเหตุผล (ออกแบบเพื่อรักษาร่องรอยการตรวจสอบ)

## 10. ขั้นตอน rollback

1. คืน `public/index.html` และ `public/api.php` จากชุดสำรอง v4 (โฟลเดอร์ `sea\` ต้นฉบับหรือ backup)
